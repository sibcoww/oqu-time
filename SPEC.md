# Техническое задание — SchoolScheduler

**Версия:** 0.2  
**Статус:** рабочее ТЗ для разработки  
**Платформа:** Windows 10/11 x64  
**Формат приложения:** локальное desktop-приложение  
**Основной пользователь:** завуч / диспетчер расписания  
**Интернет:** для основной работы не требуется  
**Язык разработки:** C# / .NET  
**UI:** WPF  
**Архитектурный подход:** MVVM  
**Хранилище:** SQLite + Entity Framework Core  
**Алгоритм расписания:** Google OR-Tools CP-SAT  
**Импорт/экспорт Excel:** ClosedXML  
**Распространение:** self-contained Windows installer

---

# 1. Цель проекта

Разработать локальное Windows-приложение, которое помогает завучу или диспетчеру школы автоматически составлять учебное расписание с учетом:

- классов;
- учителей;
- предметов;
- педагогической нагрузки;
- количества часов в неделю;
- учебных дней;
- смен;
- кабинетов;
- групп;
- доступности учителей;
- фиксированных уроков;
- обязательных ограничений;
- желательных ограничений;
- норм и рекомендаций Республики Казахстан;
- ручных правок пользователя.

Результатом работы программы должно быть готовое расписание, которое можно просмотреть, проверить, изменить вручную, оптимизировать и экспортировать в удобный формат.

---

# 2. Пользователь программы

Программа предназначена для одного локального пользователя:

- завуча;
- диспетчера расписания;
- другого сотрудника школы, ответственного за составление расписания.

В первой версии:

- аккаунты не нужны;
- авторизация не нужна;
- сервер не нужен;
- облачная синхронизация не нужна;
- отдельная установка базы данных не нужна.

Пользователь устанавливает программу через обычный установщик и работает локально на одном ПК.

---

# 3. Основной пользовательский сценарий

## 3.1. Первый запуск

При первом запуске приложение открывает мастер настройки школы.

### Шаг 1. Основные данные

Поля:

- название школы;
- учебный год, например `2026–2027`;
- язык интерфейса;
- количество учебных дней в неделе: 5 или 6;
- регион / страна — в первой версии Казахстан;
- флаг `Использовать проверку норм РК`.

После завершения создается локальный проект школы.

---

## 3.2. Расписание звонков

Пользователь задает:

- количество смен;
- время начала каждой смены;
- количество уроков в смене;
- наличие нулевого урока;
- время начала и окончания каждого урока;
- продолжительность перемен;
- большую перемену;
- интервал между первой и второй сменой.

Пример:

| Урок | Начало | Конец |
|---|---:|---:|
| 0 | 07:10 | 07:55 |
| 1 | 08:00 | 08:45 |
| 2 | 08:50 | 09:35 |
| 3 | 09:50 | 10:35 |
| 4 | 10:40 | 11:25 |

Программа должна уметь проверять введенное расписание звонков на ошибки и, при включенной проверке норм РК, показывать нормативные предупреждения.

---

# 4. Классы

Пользователь должен иметь возможность добавлять классы:

- вручную;
- массово.

Пример массового создания:

- параллели: `1–11`;
- буквы: `А, Б, В, Г`.

Результат:

- 1А;
- 1Б;
- 2А;
- 2Б;
- и т.д.

Для каждого класса хранить:

- идентификатор;
- отображаемое название;
- параллель;
- букву;
- смену;
- учебные дни;
- максимально допустимое количество уроков в день;
- классного руководителя — необязательно;
- пользовательские ограничения;
- активен / архивный.

---

# 5. Совмещенные классы / классы-комплекты

В реальной нагрузке школы встречаются обозначения вида:

- `5/6А`;
- `7/8А`;
- `9/10А`.

Программа не должна автоматически угадывать смысл символа `/`.

При импорте такого обозначения нужно показать пользователю диалог:

> Обнаружено составное обозначение класса `5/6А`.
>
> Выберите тип:
>
> - единый класс-комплект;
> - два отдельных класса;
> - оставить как отдельное название;
> - решить позже.

Для класса-комплекта должна быть возможность объединить несколько классов в один учебный поток для части или всех уроков.

Точная семантика таких обозначений требует подтверждения у сотрудника школы перед окончательной реализацией алгоритма.

---

# 6. Учителя

Для учителя хранить:

- ФИО;
- сокращенное отображаемое имя — необязательно;
- предметы, которые он ведет;
- кабинеты, в которых он может работать;
- доступные дни;
- недоступные дни;
- доступные уроки по каждому дню;
- максимально допустимое количество уроков в день;
- максимально допустимое количество окон;
- возможность нулевого урока;
- пользовательские пожелания;
- активен / архивный.

Один учитель может вести:

- несколько предметов;
- несколько классов;
- разные группы одного класса.

---

# 7. Предметы

Для предмета хранить:

- полное название;
- короткое название;
- категорию;
- уровень сложности;
- тип: обязательный / факультатив / вариативный;
- разрешены ли сдвоенные уроки;
- рекомендуемое максимальное количество уроков предмета в день;
- набор допустимых типов кабинетов;
- дополнительные нормативные параметры.

Примеры:

- Математика / Матем;
- Русский язык и литература / Рус яз и лит-ра;
- Информатика / Информ;
- Физическая культура / Физ-ра;
- История Казахстана / Ист Каз.

---

# 8. Кабинеты

Для кабинета хранить:

- идентификатор;
- название;
- номер;
- тип;
- вместимость — необязательно;
- доступность по дням и урокам;
- активен / архивный.

Типы кабинетов:

- обычный;
- информатика;
- лаборатория;
- химия;
- физика;
- мастерская;
- спортзал;
- ФОК;
- другое.

Должны поддерживаться как номера (`12`, `17`, `22`), так и текстовые значения (`спортзал`, `ФОК`).

---

# 9. Группы

Программа должна поддерживать деление класса на группы.

Пример:

`6Б`:

- группа 1 — английский язык — учитель А;
- группа 2 — английский язык — учитель Б.

Две группы одного класса могут заниматься одновременно, если:

- назначены разные преподаватели;
- используются разные кабинеты или допускается одно помещение;
- отсутствует конфликт ресурсов.

Для группы хранить:

- название;
- родительский класс;
- предмет или назначение — необязательно;
- преподавателя — через нагрузку;
- кабинет — через нагрузку.

---

# 10. Учебная нагрузка

Основная единица исходных данных для генерации расписания — строка нагрузки.

Формат:

| Учитель | Предмет | Класс | Часов/нед | Кабинет | Группа | Нулевой урок |
|---|---|---|---:|---|---|---|

Одна строка означает отдельное учебное назначение.

Пример:

`Бакенова Ж.А. | Математика | 7Б | 5 | 12 | — | нет`

`Бакенова Ж.А. | Информатика | 7/8А | 2 | 12 | — | нет`

Один учитель может иметь несколько строк нагрузки.

---

# 11. Дробная нагрузка

В предоставленном реальном файле встречаются значения:

- `0,25` часа в неделю;
- `0,5` часа в неделю.

Программа не должна без подтверждения автоматически переводить такие значения в конкретную периодичность.

При импорте дробной нагрузки показать диалог:

> Обнаружена нагрузка 0,5 часа в неделю.
>
> Как проводить занятие?
>
> - 1 урок раз в 2 недели;
> - задать количество занятий за четверть;
> - задать количество занятий за учебный период;
> - настроить вручную.

Для 0,25 аналогично.

Архитектура должна поддерживать циклическое расписание и периодичность занятий, даже если полноценный календарный режим будет реализован не в первой версии.

---

# 12. Импорт данных

Пользователь должен иметь два способа заполнения нагрузки:

1. импорт Excel;
2. ручное заполнение через программу.

## 12.1. Рекомендуемый Excel-шаблон

Программа должна уметь сама создавать шаблон `.xlsx`.

Колонки:

- ФИО учителя;
- предмет;
- короткое название предмета;
- класс;
- часов в неделю;
- кабинет;
- группа;
- нулевой урок;
- комментарий — необязательно.

## 12.2. Импорт стороннего Excel

В перспективе программа может поддерживать мастер сопоставления колонок.

Например пользователь выбирает:

`Столбец B -> Учитель`

`Столбец C -> Предмет`

`Столбец E -> Класс`

`Столбец F -> Часов в неделю`

## 12.3. Проверка импорта

После импорта показать отчет:

> Импортировано: 24 учителя  
> Найдено: 18 классов  
> Найдено: 21 предмет  
> Найдено: 14 кабинетов
>
> Предупреждения:
>
> - найдено 3 составных класса;
> - найдено 4 строки с дробной нагрузкой;
> - у 2 строк отсутствует кабинет;
> - обнаружено неизвестное обозначение группы.

Пользователь должен подтвердить импорт после просмотра ошибок.

# 13. Ограничения

Ограничения делятся на два основных типа.

## 13.1. Жесткие ограничения

Нарушать нельзя.

Примеры:

- один учитель не может вести два урока одновременно;
- один полный класс не может находиться на двух уроках одновременно;
- кабинет не может быть занят двумя несовместимыми уроками одновременно;
- учитель не может быть назначен в недоступное время;
- класс должен заниматься только в разрешенную смену;
- должно быть размещено требуемое количество занятий;
- фиксированный урок нельзя переносить;
- группа должна соблюдать собственные ограничения;
- нельзя использовать неподходящий кабинет, если он обязательный;
- должны соблюдаться активированные нормативные ограничения.

## 13.2. Мягкие ограничения

Их можно нарушить, если идеальное расписание невозможно, но за нарушение начисляется штраф.

Примеры:

- минимизировать окна преподавателей;
- равномерно распределять уроки класса по дням;
- равномерно распределять один предмет по неделе;
- не ставить несколько тяжелых предметов подряд;
- не ставить слишком много тяжелых предметов в один день;
- минимизировать последние уроки;
- минимизировать нулевые уроки;
- учитывать пожелания преподавателей;
- по возможности не ставить один предмет дважды за день;
- ставить факультативы в менее загруженные дни.

Для мягких ограничений должен существовать вес / приоритет.

Пример:

- низкий;
- средний;
- высокий;
- критичный.

Или внутреннее числовое значение штрафа.

---

# 14. Пользовательские ограничения

Пользователь должен иметь возможность создать правило без изменения кода.

Примеры:

- Иванова не работает по средам;
- Петров может работать только с 1 по 4 урок;
- физкультуру нельзя ставить первым уроком;
- 7Б учится только во вторую смену;
- химия проводится только в кабинете 14;
- 10А не может иметь больше 7 уроков;
- урок математики 5А зафиксирован на понедельник 2-м уроком;
- для конкретного учителя допускается максимум 1 окно в день.

---

# 15. Проверка исходных данных до генерации

Перед запуском генератора программа должна проверить данные.

Примеры ошибок:

> 5А имеет 34 обязательных часа, но доступно только 30 временных слотов.

> Учитель Иванов должен провести 28 уроков, но его доступность позволяет поставить максимум 24.

> Для двух обязательных занятий одновременно требуется один и тот же единственный кабинет.

> У нагрузки не указан предмет.

> Класс 7Б не назначен ни на одну смену.

Кнопка `Составить расписание` должна быть недоступна при критических ошибках.

---

# 16. Нормы Республики Казахстан

Нормативные правила должны быть реализованы как отдельный конфигурируемый модуль, а не зашиты непосредственно в UI или генератор.

Причина: требования могут изменяться по учебным годам.

Для набора нормативов хранить:

- страну;
- учебный год;
- версию;
- дату актуальности;
- источник / примечание;
- набор жестких правил;
- набор рекомендаций;
- таблицу сложности предметов;
- ограничения нагрузки по параллелям;
- правила длительности уроков и перемен;
- правила для смен;
- специальные правила для начальной школы.

В интерфейсе:

`[x] Учитывать нормы РК при составлении`

После генерации отдельная кнопка:

`Проверить по нормам РК`

Пример результата:

> Проверка по нормам РК — 2026/27
>
> ✓ Недельная нагрузка  
> ✓ Длительность уроков  
> ✓ Перемены  
> ✓ Смены  
> ✓ Обязательные ограничения  
> ⚠ 3 рекомендации по распределению сложности  
> ❌ 0 критических нарушений

**Важно:** перед выпуском программы конкретные нормативные значения должны быть повторно сверены с действующими официальными документами РК на соответствующий учебный год.

---

# 17. Сложность предметов

Предметы должны иметь нормативный или пользовательский вес сложности.

Он используется как мягкое ограничение при оптимизации.

Пример логики:

- тяжелые предметы не концентрировать в один день;
- не ставить слишком много тяжелых уроков подряд;
- по возможности распределять нагрузку класса равномерно по неделе.

Пользователь должен иметь возможность просмотреть и при необходимости изменить веса до генерации.

---

# 18. Генерация расписания

Для генерации использовать constraint solver на базе Google OR-Tools CP-SAT.

## 18.1. Основная задача

Для каждого занятия определить:

- день недели;
- номер урока;
- смену;
- кабинет;
- преподавателя;
- класс / группу.

## 18.2. Первый этап

Найти решение, удовлетворяющее всем жестким ограничениям.

Если решения нет, программа должна объяснить возможные причины.

Не показывать пользователю просто `No solution`.

Пример:

> Расписание не удалось составить.
>
> Возможные конфликты:
>
> - учителю Ивановой не хватает 2 доступных временных слотов;
> - кабинет информатики требуется одновременно для 7А и 7Б;
> - для 5Б задано больше обязательных уроков, чем доступно времени.

## 18.3. Второй этап

После получения допустимого расписания оптимизировать мягкие ограничения.

Результат должен иметь оценку качества.

Пример:

> Качество: 94/100
>
> Жестких нарушений: 0
>
> Штрафы:
>
> - 3 окна у преподавателей;
> - у 8Б тяжелый понедельник;
> - математика 7А распределена неравномерно.

---

# 19. Несколько вариантов расписания

Программа должна в перспективе уметь генерировать несколько допустимых вариантов.

Например:

- Вариант A — 96/100;
- Вариант B — 94/100;
- Вариант C — 91/100.

Пользователь выбирает наиболее подходящий.

Для MVP допустимо сначала реализовать генерацию одного лучшего найденного варианта.

---

# 20. Просмотр готового расписания

Необходимо несколько режимов просмотра.

## 20.1. По классу

Пример:

| Урок | Пн | Вт | Ср | Чт | Пт |
|---|---|---|---|---|---|
| 1 | Математика | Русский | Физика | ... | ... |
| 2 | Английский | Математика | ... | ... | ... |

## 20.2. По учителю

Показывает индивидуальное расписание выбранного преподавателя.

## 20.3. По кабинету

Показывает занятость кабинета.

## 20.4. Общее расписание школы

Табличное отображение всех классов.

---

# 21. Ручное редактирование

После генерации пользователь может менять расписание вручную.

Желательный UX:

- drag & drop урока;
- выбор ячейки;
- контекстное меню;
- обмен двух уроков местами;
- закрепление урока;
- удаление / возврат в список нераспределенных занятий.

При любом изменении программа сразу проверяет конфликты.

Пример:

> Невозможно переместить урок.
>
> Учитель уже ведет 6Б в это время.

Для мягкого нарушения:

> Перемещение возможно, но создаст окно у преподавателя.
>
> Продолжить?

---

# 22. Фиксация уроков

Пользователь может закрепить урок.

Фиксированный урок:

- не перемещается при повторной оптимизации;
- учитывается генератором как жесткое ограничение.

Пример:

`10А | НВТП | Пятница | 5 урок | Закреплено`

---

# 23. Повторная оптимизация

После ручных правок кнопка:

`Оптимизировать оставшееся расписание`

# 37. Правила безопасной разработки с ИИ

4. не принимать огромные изменения сразу;
5. всегда запускать сборку;

7. сохранять тестовые наборы школьных данных;
8. перед рефакторингом делать отдельный commit;
9. не разрешать ИИ удалять тесты только потому, что они перестали проходить;
10. проверять UI вручную после каждого UI-этапа;
11. хранить ТЗ в репозитории;

# 38. Git workflow для AI-first разработки

Для простоты на начальном этапе:

- `main` — стабильная версия;
- отдельная ветка на крупный этап.

Пример:

```text
feature/teacher-crud
feature/excel-import
feature/scheduler-v1
feature/manual-editing
```

После завершения этапа:

1. build;
2. tests;
3. ручная проверка;
4. commit;
5. merge в main.

Сообщения commit:

```text
feat: add teacher management
```

```text
        ↓
```

- знать, что такое OR-Tools;
- вручную разбираться с зависимостями .NET.
